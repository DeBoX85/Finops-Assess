# 11 Azure cost governance: what Microsoft documents, and what a Reader can see (read 2026-10-20)

## 1. What "cost governance" means in Microsoft guidance
- VERIFIED. CAF: "Cost governance is the continuous process of implementing policies or controls to limit spending and costs" (L:/azure/architecture/aws-professional/eks-to-aks/cost-management, section Cost governance, which defers to CAF governance).
- VERIFIED. CAF "Enforce cloud governance policies" (L:/azure/cloud-adoption-framework/govern/enforce-cloud-governance-policies) lists for cost: enforce a tagging strategy; automate cost allocation with tags; build a management group hierarchy so policy, access and spending can be governed; restrict resource types (policy "Not allowed resource types"); restrict regions ("Allowed locations"); use infrastructure as code.
- VERIFIED. CAF "Create and scale Azure subscriptions" (L:/azure/cloud-adoption-framework/ready/azure-setup-guide/initial-subscriptions#govern-your-subscriptions): apply a budget and cost alerts "to each subscription"; define mandatory tags for ownership, cost center, environment and application; apply Azure Policy at management group level.
- VERIFIED. CAF "Track costs" (L:/azure/cloud-adoption-framework/ready/azure-best-practices/track-costs): cost control depends on a well-managed environment; tags commonly needed are business unit, department, billing code, geography, environment, project, workload or application.
- VERIFIED. WAF Cost Optimization principles (L:/azure/well-architected/cost-optimization/principles): "Develop cost-management discipline" (cost model, accountability model, budgets with threshold notifications), "Design and enforce cost guardrails", "Implement cost alerts when spending approaches predefined budget thresholds", "capture and classify expense" for showback and chargeback. The WAF checklist items CO:01 culture, CO:02 cost model, CO:04 spending guardrails are named on L:/azure/well-architected/cost-optimization/collect-review-cost-data (related links only; I did not open CO:04 itself).
- VERIFIED. FinOps Foundation capabilities as documented by Microsoft (L:/cloud-computing/finops/framework/capabilities): Understand (Data ingestion, Allocation, Reporting, Anomaly management), Quantify (Planning, Forecasting, Budgeting, Benchmarking, Unit economics), Optimize (...), Manage the practice (Policy and governance, Invoicing and chargeback, FinOps assessment ...). Governance guidance (L:/cloud-computing/finops/framework/manage/governance): enforce tagging, monitor budget and anomaly alerting, block or audit expensive SKUs, "start small with audit policies and expand slowly". NOTE: audit-only tag policy is therefore a legitimate early maturity step, not a defect.

## 2. Tags: facts that shape the hygiene check
All VERIFIED from L:/azure/azure-resource-manager/management/tag-resources and CAF tagging page (L:/azure/cloud-adoption-framework/ready/azure-best-practices/resource-tagging).
- Tags apply to resources, resource groups and subscriptions, NOT to management groups.
- Tag NAMES are case-insensitive for operations, but the resource provider may keep the casing given and "you see that casing in cost reports". Tag VALUES are case-sensitive: `environment: Production` and `environment: production` are different values and "appear separately in cost reports and resource queries".
- Max 50 name/value pairs per resource; name max 512 chars, value 256 (storage account names 128). Some services allow only 15 tags (Automation, CDN, public and private DNS, Log Analytics saved search). Name cannot contain `< > % & \ ? /`.
- Resources do NOT inherit tags from resource group or subscription (policy or Cost Management inheritance is needed).
- Not every resource type supports tags (list: L:/azure/azure-resource-manager/management/tag-support, not parsed yet). Classic resources do not.
- Tags are plain text and show up in cost reports, deployment history and logs; CAF says do not store sensitive values. Consequence for F-CAT: tag VALUES (owner emails, names) are customer data. Store counts and variant shapes, not values, for high-cardinality keys.
- Cost Management only sees a tag in usage data if it is on the resource, was applied more than 24 hours ago, and the resource type emits tags in usage (L:/azure/cost-management-billing/costs/understand-cost-mgt-data#how-tags-are-used-in-cost-and-usage-data).
- CAF tag categories (examples, not a standard to hard-code): functional (app, tier, env, region), classification (criticality, confidentiality, sla), accounting (department, program, costcenter), purpose (businessprocess), ownership (businessunit, opsteam). CAF advises lowercase tag names.
- REST "Tags - List": GET /subscriptions/{id}/tagNames?api-version=2021-04-01 returns a union of predefined, resource, resource group and subscription tag names with usage counts and value counts; may return a cached result on large estates (L:/rest/api/resources/tags/list). Read only. Useful as a cross-check, not as the main source.

## 3. Tag inheritance (two different mechanisms)
- VERIFIED. Cost Management tag inheritance (L:/azure/cost-management-billing/costs/enable-tag-inheritance): copies billing, subscription and resource group tags onto child usage records. "Inherited tags are applied to child resource usage records and not the resources themselves." Available for EA, MCA and MPA (Azure plan); the page does not list pay-as-you-go. If a resource tag has the same name, the resource tag wins by default. Takes 8 to 24 hours to apply to the current month. Cost Management Reader can view; Contributor edits. Scopes table says "View only - Available at subscription scope only" for Azure RBAC roles.
- VERIFIED. Setting resource type is Microsoft.CostManagement/settings, kind taginheritance, name taginheritance, property preferContainerTags (bicep reference, api versions up to 2026-06-01). UNVERIFIED: the exact GET path and response for reading it, and whether Reader can call it. Not usable by F-CAT until read once on a real scope.
- VERIFIED. Azure Policy route (L:/azure/azure-resource-manager/management/tag-policies) changes the resource tags themselves: built-ins "Inherit a tag from the resource group (if missing)", "Inherit a tag from the subscription (if missing)" (effect modify, existing resources need a remediation task), "Append ..." (older, append effect), "Require a tag on resources / resource groups" and "Require a tag and its value ..." (deny), "Add a tag to resources ..." (modify). The page lists the definition GUIDs in portal links (e.g. Require a tag on resources 871b6d14-10aa-478d-b590-94f262ecfa99, Require a tag and its value on resources 1e30110a-5ceb-460c-a204-c1c3969c6d62, Inherit a tag from the resource group cd3aa116-8754-49c9-a813-ad46512ece54, ... if missing ea3f2387-9b95-492a-a190-fcdc54f7b070, Inherit a tag from the subscription b27a0cbd-a167-4dfa-ae64-4337be671140, ... if missing 40df99da-1232-49b1-a39a-6da8d878f469). The "Require" ones do not apply to resource groups; separate RG variants exist (96670d01-..., 8ce3da23-...).
- VERIFIED (single source, a small model summarised the GitHub JSON): "Require a tag on resources" has parameter `tagName` and a hard-coded deny effect (github.com/Azure/azure-policy, built-in-policies/policyDefinitions/Tags/RequireTag_Deny.json, read 2026-10-20). Other tag definitions' parameter names UNVERIFIED. If a customer used a custom definition or an initiative, the tag names cannot be read reliably: report as "unclassified policy", never guess.
- FinOps Allocation (L:/cloud-computing/finops/framework/understand/allocation, VERIFIED): top-down approach, enable tag inheritance, use Azure Policy to enforce and "use compliance as a KPI for your tagging strategy", allocation rules to move shared costs, cm-resource-parent tag to group related resources. Expect several tagging cycles.
- VERIFIED. Cost allocation RULES are a billing-account feature only: the RBAC scopes table says "Feature not available for Azure RBAC scopes". A Reader on subscriptions cannot see them. Report "not assessed, because allocation rules live on the billing account scope".

## 4. Azure Policy data a Reader can query
- VERIFIED (L:/azure/governance/resource-graph/reference/supported-tables-resources). ARG table `policyresources` holds microsoft.authorization/policyassignments, policydefinitions, policysetdefinitions, policyexemptions, microsoft.policyinsights/policystates, componentpolicystates. Inherited assignments need the AuthorizationScopeFilter option (API 2021-06-01-preview or later), default AtScopeAndBelow, and AtScopeAndAbove/AtScopeAboveAndBelow to include parents (L:/azure/governance/resource-graph/concepts/query-language#query-scope). This matters: policies assigned at management group or tenant root are invisible to a subscription-scoped query unless the filter is used. Our arg.query has no such option yet.
- VERIFIED. Compliance sample queries use `PolicyResources | where type == 'microsoft.policyinsights/policystates'` with properties.complianceState, policyAssignmentId, resourceId.
- VERIFIED. Exemptions: compliance state Exempt, sub state in properties.stateDetails.complianceSubState (Waiver or Mitigated) (L:/azure/governance/policy/concepts/exemption-structure). UNVERIFIED: exemption expiry property name (I believe properties.expiresOn).
- UNVERIFIED: assignment property names for enforcementMode and parameters in ARG; policyAssignments.properties.parameters.tagName.value is my expectation from the definition parameter name.
- Not found in ARG: management locks. `authorizationresources` lists role assignments etc.; locks appear only as a child governanceassignments type. Lock listing would need an ARM GET (not researched). Locks are low value for cost; parked.
- Role: Reader is enough to read policy via ARG for subscriptions it covers (general RBAC knowledge, UNVERIFIED for this table).

## 5. Budgets
- VERIFIED. List: GET https://management.azure.com/{scope}/providers/Microsoft.Consumption/budgets?api-version=2026-06-01 (L:/rest/api/consumption/budgets/list). Fields: properties.amount, category (Cost), timeGrain (Monthly, Quarterly, Annually; Billing* only for WD customers), timePeriod.startDate/endDate (end defaults to 10 years from start), currentSpend.amount, forecastSpend.amount (only if a forecast alert exists), filter (dimensions, tags), notifications (up to five; each has enabled, operator, threshold 0..1000 percent, thresholdType Actual|Forecasted, contactEmails, contactRoles, contactGroups, locale). Action groups only at subscription or resource group scope.
- VERIFIED. Budget scopes: management group, subscription, resource group (RBAC); billing scopes for EA, MCA, individual (L:/azure/cost-management-billing/costs/tutorial-acm-create-budgets). Management group budgets need a single currency across subscriptions. Budget evaluation uses actual cost, not amortised, and now includes reservation purchases. New subscriptions can take up to 48 hours before cost features work.
- VERIFIED. A budget "actively monitors and alerts you only while it remains valid" (timePeriod), so an expired budget is no control (L:/azure/cost-management-billing/automate/automate-budget-creation).
- VERIFIED. Permissions: Reader and Cost Management Reader can VIEW budgets (read only); Contributor or Cost Management Contributor can create. Cost Management Reader role actions include Microsoft.Consumption/*/read and Microsoft.CostManagement/*/read (L:/azure/cost-management-billing/costs/understand-work-scopes, L:/azure/role-based-access-control/built-in-roles/management-and-governance#cost-management-reader). "Read access is required to view budgets for Azure EA subscriptions."
- PRIVACY: budget responses contain email addresses. Collector must keep only counts and booleans (has email, has role, has action group), never the addresses.
- FinOps Budgeting (L:/cloud-computing/finops/framework/quantify/budgeting, VERIFIED): start with cost alerts, on actual and forecast, at the primary scope; quarterly and yearly budgets if rollover matters; automate budget creation for new subscriptions and resource groups; action-group automation "especially helpful on test subscriptions".
- CAF (see 1): a budget and alerts on each subscription.

## 6. Anomaly alerts and scheduled alerts
- VERIFIED (L:/azure/cost-management-billing/understand/analyze-unexpected-charges). Anomaly detection runs per subscription daily, compares to a forecast from the last 60 days, runs 36 hours after the end of the UTC day, public cloud only (not Azure Government or sovereign clouds). Anomaly alert RULES exist only at subscription scope, max five rules per subscription, created as a scheduled action of kind InsightAlert, viewId ending ms:DailyAnomalyByResourceGroup. Creating needs Cost Management Contributor or Microsoft.CostManagement/scheduledActions/write. An anomaly email is sent once.
- VERIFIED. Scheduled actions "kind": Email | InsightAlert; status Enabled | Expired | Disabled (L:/rest/api/cost-management/scheduled-actions/list, version 2026-06-01).
- VERIFIED (partly). The REST page I opened lists PRIVATE scheduled actions for the caller (GET /providers/Microsoft.CostManagement/scheduledActions). The SDK reference describes listByScope as "List all shared scheduled actions within the given scope", scope subscriptions/{id}, filter on properties/viewId, "Insight Alerts are only available on subscription scope" (Java SDK docs). UNVERIFIED: whether an anomaly rule created in the portal is stored shared or private, and so whether a Reader sees other people's rules. Therefore "no anomaly alert found" must be low confidence and worded "not visible to this identity".
- VERIFIED. Recipients are email addresses (privacy, same rule as budgets).
- FinOps Anomaly management (L:/cloud-computing/finops/framework/understand/anomalies, VERIFIED): subscribe to anomaly alerts for each subscription.

## 7. Cost data exports (data ingestion capability)
- VERIFIED. List: GET {scope}/providers/Microsoft.CostManagement/exports?api-version=2026-06-01, supports subscription, resource group, management group and billing scopes, optional $expand=runHistory (last run status: Completed, Failed, Timeout, DataNotAvailable ...). Export types include ActualCost, AmortizedCost, FocusCost, PriceSheet, Reservation*. Schedule status Active or Inactive. Destination includes the storage account resource ID (customer resource ID: redact).
- VERIFIED. Reader can view exports (read only) per the RBAC scopes table.

## 8. Management group and subscription structure
- VERIFIED. Tags cannot be set on management groups. CAF landing zone guidance: policy at management group level; hierarchy so each team gets the right visibility (track-costs page).
- UNVERIFIED: how much of the hierarchy a Reader can see. The existing collector reads management_groups; a user only sees groups where they have read access.

## 11. Phase 2 REST shapes re-read (2026-10-20)
- VERIFIED (L:/rest/api/cost-management/exports/list, version 2026-06-01): response `value[]` of Export. `properties.schedule` is absent for a one-time export; when present it has `recurrence` (Daily, Weekly, Monthly, Annually) and `status` (Active, Inactive; Inactive means the schedule is paused). `$expand=runHistory` returns `properties.runHistory.value[]` of ExportRun with `properties.status` (Queued, InProgress, Completed, Failed, Timeout, NewDataNotAvailable, DataNotAvailable), `processingEndTime`, `error.code`, `submittedBy`. `deliveryInfo.destination` holds `resourceId` (storage account), `container`, `rootFolderPath`: all customer data, never stored. The doc says runHistory is "the last run of each export", but the runHistory array may hold several runs; the collector picks the latest by processingEndTime (UNVERIFIED live).
- VERIFIED (L:/rest/api/cost-management/scheduled-actions/list-by-scope, 2026-06-01): "List all shared scheduled actions within the given scope". `kind` Email | InsightAlert (InsightAlert: anomaly information, subscription scope only, daily frequency, no email when nothing is detected). `properties.status` Enabled | Expired | Disabled. `properties.notification.to` is the e-mail list (never stored). Private scheduled actions are listed by a different call; whether a portal-created anomaly rule is shared or private stays UNVERIFIED.
- NOT RE-READ this pass: the budgets list response shape beyond the fields recorded in section 5; `notifications` is documented as a dictionary keyed by name, and the collector accepts a list as well, because a live response was never seen.
